# Shop Personalization — Intersport Side Guide

> **Scope**: Everything to build on the Intersport side (Supabase project + public shop page) to support the **"Ma boutique"** feature on Footspot.
> **Counterpart guide (Footspot side)**: `/home/g1/.ved/footspot/footspot-web/INTERSPORT_INTEGRATION.md` — see Phase 5.
> **Sibling guide (order lifecycle)**: `FOOTSPOT_INTEGRATION.md` in this repo.

This feature lets each Footspot club director customize his own shop page on Intersport without leaving Footspot. Three things are editable from Footspot:

1. **Slogan** — displayed under the club name on the public shop page.
2. **Accent color** — used for buttons, links, prices and active filter pill on the public shop page.
3. **Per-product discount %** — absorbed entirely on the **club's** margin; Intersport keeps its margin intact.

Nothing in this feature is editable from the Intersport admin panel — Footspot is the only writer. The Intersport admin panel may eventually surface these values **read-only** so the operator can sanity-check what the club has set, but write paths are exclusively the inbound endpoints below.

---

## Core principles

- **Margin-only absorption**. Intersport's per-product margin is **never** touched by a discount. The club's margin pays for the discount, and if the discount would push the club margin below zero, the request is **rejected with 422**. The Intersport price floor (`price_cents − intersport_margin_cents`) is hard.
- **Footspot is the writer; Intersport is the source of truth**. Footspot caches what it last pushed. The Intersport row is canonical. The shop page renders from the Intersport row only.
- **No partial saves**. A bulk discount push is all-or-nothing: if any row fails the margin guard, the whole batch is rejected and Intersport state is unchanged.
- **Same auth pipeline as the order endpoints**: `X-Intersport-Partner-Id` + HMAC + Bearer (per-club `api_token`). The slogan and accent color are written by the **director's club** only, not by another club. The per-club token enforces this — Bearer resolves to a `clubs.id`, and that's the club that gets written.

## Phase 1 — Database migrations

> **Rule**: never alter existing columns. Only additions.

### 1.1 `clubs` table additions

```sql
ALTER TABLE public.clubs
  ADD COLUMN slogan        text,                              -- * free text shown under the club name on the public shop page; NULL = no slogan
  ADD COLUMN accent_color  text                                -- * hex color "#RRGGBB" used for buttons, links, prices on the public shop page
                            CHECK (accent_color IS NULL OR accent_color ~ '^#[0-9A-Fa-f]{6}$'),
  ADD COLUMN shop_config_updated_at timestamptz,               -- * audit timestamp; bumped on any update via update-shop-config
  ADD COLUMN shop_config_updated_via text                      -- * "footspot" | "intersport_admin"; for v1 always "footspot"
                            CHECK (shop_config_updated_via IS NULL OR shop_config_updated_via IN ('footspot', 'intersport_admin'));
```

> Slogan: max 80 characters enforced at the endpoint layer, not the column (let the DB accept longer for future flexibility). No newlines (`\n`, `\r`) — rejected at the endpoint.
>
> `accent_color` default behavior on the shop page render: when NULL, fall back to Intersport's brand red `#E2001A`.

### 1.2 `product_discounts` table *(new)*

One row per `(club_id, product_reference)` where the club has set a discount > 0. Rows with `discount_pct = 0` are also kept (audit trail of "this club had a discount, then cleared it"). Hard-cap at 80 % matches Footspot's check.

```sql
CREATE TABLE public.product_discounts (
  id                bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  club_id           uuid NOT NULL REFERENCES public.clubs(id) ON DELETE CASCADE,
  product_reference text NOT NULL,                            -- * matches products.reference (or product_variants.reference)
  discount_pct      smallint NOT NULL CHECK (discount_pct BETWEEN 0 AND 80),
  updated_at        timestamptz NOT NULL DEFAULT now(),
  updated_via       text NOT NULL DEFAULT 'footspot'          -- * always 'footspot' in v1
                    CHECK (updated_via IN ('footspot', 'intersport_admin')),

  UNIQUE (club_id, product_reference)
);

CREATE INDEX product_discounts_club_idx
  ON public.product_discounts(club_id)
  WHERE discount_pct > 0;
```

### 1.3 Products: expose margin to the validator

The margin guard needs to read each product's `intersport_margin_pct` (the part Intersport keeps) and `club_margin_pct` (the part the club keeps). These already exist on the product or product-variant table — verify the names match. If they don't, add them:

```sql
-- * only if not already present
ALTER TABLE public.products
  ADD COLUMN intersport_margin_pct smallint NOT NULL DEFAULT 0
              CHECK (intersport_margin_pct BETWEEN 0 AND 100),
  ADD COLUMN club_margin_pct       smallint NOT NULL DEFAULT 0
              CHECK (club_margin_pct BETWEEN 0 AND 100);
```

> If the existing schema stores `cost_cents` and `sale_price_cents` instead of percentages, derive `club_margin_pct` on the fly in the validator: `club_margin_pct = (sale_price_cents − cost_cents − intersport_margin_cents) / sale_price_cents * 100`. The exact formula depends on how the existing pricing model is structured — confirm before coding.

## Phase 2 — Inbound endpoints (called by Footspot)

All endpoints live under `supabase/functions/`. Auth follows the same pipeline as the order endpoints:

```
1. Read header X-Intersport-Partner-Id   → resolve THIS instance's partner row (single-tenant; just sanity-check)
2. Verify X-Signature HMAC               using FOOTSPOT_SERVICE_SECRET (env var for this Intersport instance)
3. Verify Bearer = per-club api_token    against intersport_links.api_token_hash  → resolves club_id
4. Verify X-Timestamp within ±300s
5. Verify X-Idempotency-Key for repeatable writes
```

Standard error envelope: `{ "ok": false, "error": "<code>", "message": "<human readable>", ... }`.

---

### `update-shop-config` — POST

**Caller**: Footspot's `intersport-update-shop-config` edge function.
**Auth**: HMAC + per-club Bearer (the club whose shop config is being changed).

**Input**
```json
{
  "intersport_club_id": "<uuid>",
  "slogan": "Les Raptors du 93",
  "accent_color": "#2F983F"
}
```

- `intersport_club_id` MUST match the `club_id` resolved from the Bearer. Reject 403 `forbidden_cross_club` if not.
- Either field may be omitted; sending `null` clears the field.
- `slogan`: length ≤ 80, no newlines. Reject 422 `slogan_too_long` / `slogan_invalid_chars`.
- `accent_color`: regex `^#[0-9A-Fa-f]{6}$`. Reject 422 `invalid_color`.

**Logic**
1. Validate inputs.
2. UPDATE `clubs` SET `slogan = COALESCE($1, slogan)`, `accent_color = COALESCE($2, accent_color)`, `shop_config_updated_at = now()`, `shop_config_updated_via = 'footspot'` WHERE `id = $club_id`.
   - For explicit clearing (`slogan: null` in the payload), use a sentinel — Footspot must send the field with JSON `null`, not omit it. Distinguish: omitted = leave alone, present-and-null = clear.
3. Return `{ ok: true, synced_at: clubs.shop_config_updated_at }`.

**Idempotency**: writes are idempotent (UPDATE with the same values produces the same row). `X-Idempotency-Key` is logged for audit but not required for correctness.

### `update-product-discounts` — POST

**Caller**: Footspot's `intersport-update-product-discounts`.
**Auth**: HMAC + per-club Bearer.

**Input**
```json
{
  "intersport_club_id": "<uuid>",
  "discounts": [
    { "product_reference": "FZ9332-100FC93", "discount_pct": 10 },
    { "product_reference": "DR1695-010FC93", "discount_pct": 0  }
  ]
}
```

- `intersport_club_id` MUST match Bearer's `club_id`. Reject 403 `forbidden_cross_club`.
- Each row: `0 ≤ discount_pct ≤ 80`. Reject 422 `discount_out_of_range` (include the offending row).

**Logic — all-or-nothing transaction**
1. Begin tx.
2. For each row, look up the product by `reference`:
   - If product doesn't exist or isn't sold to this club → collect `{ product_reference, reason: "product_not_found" }`.
   - Read `club_margin_pct` for this product (per §1.3).
   - If `discount_pct > club_margin_pct` → collect `{ product_reference, reason: "discount_exceeds_margin", margin_pct: club_margin_pct }`.
3. **If any rejection collected**: rollback, return 422 with `{ ok: false, rejected: [...] }`.
4. **Otherwise**: UPSERT each row into `product_discounts` (`updated_at = now()`, `updated_via = 'footspot'`).
5. Commit. Return `{ ok: true, applied: <count>, synced_at: now() }`.

> Rationale for all-or-nothing: the director sees a list of products with a "Tout appliquer" button. If 1 of 12 rows fails, accepting the other 11 silently would create a confusing partial state. Reject the whole batch and let the director fix the offending input.

**Idempotency**: full-payload idempotency check on `X-Idempotency-Key`. If the same key returns, repeat the response from the audit log.

---

### `footspot-disconnect` — POST

**Caller**: Footspot's `intersport-club-disconnect` (director clicked "Déconnecter").
**Auth**: HMAC + per-club Bearer (the club disconnecting itself).

**Input**
```json
{ "intersport_club_id": "<uuid>" }
```

**Logic**
1. Verify `intersport_club_id == club_id` from Bearer.
2. Mark the club's shop as deactivated: set a `clubs.shop_status` (new enum `'active' | 'disconnected'`) to `'disconnected'`. New checkouts for this club are refused.
3. Existing orders in flight continue to deliver; they just won't get new ones.
4. Return `{ ok: true }`.

> Add the `clubs.shop_status` enum + column as part of this feature's migration if it doesn't exist yet.

## Phase 3 — Public shop page render changes

The public shop page already exists. Two render-time changes:

### 3.1 Use `clubs.accent_color`
- Read `clubs.accent_color` for the current club's shop subdomain.
- Inject as a CSS custom property at the page root: `<html style="--accent: {accent_color || '#E2001A'}">`.
- All buttons, link color, active filter pill, prices use `var(--accent)`. Match the wireframe's `--accent` usage on the Footspot side preview (`footspot-intersport-v3.html`).

### 3.2 Render slogan + discount
- Under the club name, show `clubs.slogan` in italic small text (matches the wireframe's `.club-slogan` class).
- For each product card in the listing, LEFT JOIN `product_discounts` for the current `club_id`. If `discount_pct > 0`:
  - Show the original price crossed out + the new price in accent color (`price * (1 − discount_pct/100)`).
  - Show a red `-{discount_pct}%` badge in the top-left corner (matches `.prod-mini-badge`).
- The discounted price is the price the buyer pays at checkout. Internally:
  - Order total to Intersport = `sum(price * (1 - discount_pct/100))`
  - **Club margin per item** drops by `price * discount_pct/100` (the discount comes out of `club_margin_cents`).
  - **Intersport margin per item** is unchanged.
  - Cagnotte / club invoice math (covered in `FOOTSPOT_INTEGRATION.md`) must use the **post-discount** price and the reduced club margin.

### 3.3 Checkout impact

When a buyer pays the discounted price, the order's `payload.items[*]` MUST include:
- `original_price_cents` — pre-discount price (for the receipt and for Footspot's reporting).
- `price_cents` — post-discount price (what the buyer actually paid).
- `discount_pct_applied` — the value at time of order; product_discounts may change later but the order is locked.
- `club_margin_cents` — recomputed at order time (after discount).
- `intersport_margin_cents` — unchanged.

Footspot's `intersport-events.order.created` consumes the same payload; ensure these fields appear in the existing payload schema before flipping the feature on.

## Open questions / future work

- **Member-only discount tier**: not in v1. Discount applies to every buyer (member or outsider). A second `discount_pct_member` column on `product_discounts` could unlock this later.
- **Time-bounded discounts**: not in v1. Discounts are active until explicitly cleared. Future: `valid_from` / `valid_to` columns.
- **Bulk discount by category**: not in v1. Director must set each product individually (UI bulk button is OK for sending many rows at once, but each product is still a discrete row).
- **Sub-domain renaming**: out of scope. The shop URL is locked at pairing time. Sub-domain changes would require DNS + cert work.
- **Shop password (private access)**: deferred to v1.1. The wireframe shows a "Visibilité boutique" toggle + a separate password card — both placeholders in v1.

### `club-products` — POST  *(to build)*

**Caller**: Footspot's `intersport-fetch-products` — populates the per-product
discount editor in the "Ma boutique" tab.

**Input**
```json
{ "intersport_club_id": "<uuid>" }
```

**Logic**
1. Verify HMAC + Bearer; `intersport_club_id` must match the Bearer's club.
2. List every product sold to this club.
3. For each, return its reference, display name, category, current price in
   cents, and the **club's** margin % (`club_margin_pct`, per §1.3 — the
   editor clamps the discount input to this value), and an image URL.

**Output**
```json
{
  "products": [
    {
      "product_reference": "FZ9332-100FC93",
      "name": "Maillot Domicile",
      "category": "Maillot",
      "price_cents": 6000,
      "margin_pct": 25,
      "image_url": "https://…"
    }
  ]
}
```
- `product_reference` MUST be the same key used by `product_discounts.product_reference` (so Footspot can LEFT JOIN its discount cache).
- `price_cents` is the pre-discount price.
- `margin_pct` is the club's margin — NOT Intersport's. A discount may not exceed it (the `update-product-discounts` margin guard is authoritative; this just drives the UI clamp).

### `club-stats` — POST  *(to build)*

**Caller**: Footspot's `intersport-fetch-stats` — the "Statistiques" tab.
Footspot relays this body **verbatim**; the shape below is exactly what the UI
renders, so field names and units (`*_cents` = integer cents) must match.

**Input**
```json
{
  "intersport_club_id": "<uuid>",
  "period": "current_week | current_month | current_season | all_time"
}
```

**Logic**
1. Verify HMAC + Bearer; `intersport_club_id` must match the Bearer's club.
2. Reject 422 `invalid_period` if `period` is not one of the four values.
3. Compute the club's sales stats over `period` and return the envelope below.

**Output**
```json
{
  "cagnotte_balance_cents": 124000,
  "cagnotte_recent_delta_cents": 40000,
  "cagnotte_transactions": [
    { "date": "15 mars", "label": "Achat maillots (24 pcs)", "amount_cents": -68000 }
  ],
  "kpis": {
    "sales_count": 87,
    "revenue_cents": 452000,
    "pending_orders_count": 3,
    "gross_margin_cents": 182000
  },
  "weekly_chart": [
    { "day": "Lun", "revenue_cents": 9800, "margin_cents": 4900 }
  ],
  "top_products": [
    {
      "product_reference": "NK-CH-FC93-006",
      "name": "Chaussettes Football Nike",
      "units_sold": 55,
      "margin_cents": 55000,
      "margin_pct": 61
    }
  ]
}
```
- `weekly_chart`: 7 entries, one per day, `day` a short label (e.g. `Lun`…`Dim`). The Footspot tab draws revenue + margin bars from these.
- `cagnotte_transactions[].date` is a display string; a negative `amount_cents` is a debit.
- All `*_cents` fields are integers.
